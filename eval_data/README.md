# Synthetic Evaluation Set

## What lives here

`synthetic_qa_v1.jsonl` — a set of question/answer pairs auto-generated by
GPT-4.1-mini against the seed PDFs in `Data/`. Each line is one pair:

```json
{
  "query": "...",
  "expected_keywords": ["...", "..."],
  "expected_doc": "filename.pdf",
  "language": "english",
  "source_page": 7,
  "source_excerpt": "first 240 chars of the source page",
  "generator_model": "gpt-4.1-mini",
  "is_synthetic": true
}
```

## How it was generated

For every page of every PDF in the seed corpus:

1. Skip pages with fewer than 40 meaningful words (covers, blank pages, tables of contents).
2. Send the page text to GPT-4.1-mini with a strict prompt: generate exactly two questions
   answerable from this passage — one in English, one in Nepali (Devanagari) — and provide
   3–5 short keywords for each that **must appear verbatim in the passage**.
3. Validate every returned pair: each keyword must be present in the source page after
   NFC normalisation and lowercasing. Pairs that fail validation are dropped at generation
   time, before they ever hit the JSONL file.
4. Cap per-document count for class balance so one long PDF can't dominate the eval.

Code: `nepal_gov_agent/eval/synthetic.py`.
Run: `python -m nepal_gov_agent.eval.generate`.

## What this set IS

- A reproducible smoke test bigger than the original 7-question harness.
- A regression signal: if a code change drops Recall@3 by 10 points, something
  is broken.
- A starting point for someone who wants to curate a real human-validated set
  later — keep the questions that survive scrutiny, throw out the rest.

## What this set is NOT

It is **not** a benchmark. There are three specific reasons:

1. **No human reviewed the questions.** The validation step only checks that the
   keywords appear in the source text. It does not check whether the question is
   sensible, whether a Nepali speaker would actually phrase it that way, or whether
   the expected keywords are the *right* answer (they may be incidental keywords that
   happen to appear on the page).

2. **The Nepali questions are LLM-translated, not native.** Native fluency is the
   thing the Nepali side of the eval is supposed to test, and a generator that is
   itself not a native Nepali speaker can't credibly produce that test.

3. **The eval and the system being evaluated share a substrate.** The generator
   read the same text the retriever reads. Lexical overlap is easy to get; semantic
   understanding is not. Numbers will look better than they should.

Anyone citing these numbers as evidence of capability without the disclaimer is
misrepresenting what they are. The benchmark report header includes the same
warning so it travels with the numbers.

## What "real" evaluation would look like

- Native-speaker review of a sample (~50 pairs) for fluency and answerability.
- Adversarial questions written by a domain expert (lawyer, civil servant) that
  test the corners — multi-hop reasoning across documents, dates, exceptions.
- A held-out set of real user queries from a deployed instance, if one exists.
- Disagreement analysis: where do humans disagree with each other on the answer?
  That gap is the ceiling of any automated metric.

If you want to fund or contribute that work, open an issue.

## Reproducibility

The JSONL file shipped with a release should be regeneratable from the same
corpus and the same model version. Models drift; if `gpt-4.1-mini` changes
under us, the regenerated set will not match byte-for-byte. The committed
file is the canonical artifact for that release tag.

Regenerate locally:

```bash
export OPENAI_API_KEY=sk-...
python -m nepal_gov_agent.eval.generate \
  --corpus Data/ \
  --out eval_data/synthetic_qa_v1.jsonl \
  --max-per-doc 20
```

Idempotent — pages already covered are skipped unless you pass `--no-resume`.
